## 2. RESOLVED — signup works, and a real card went through

*Was: "THE BLOCKER — nobody can sign up". Closed 6 Aug, later the same day.*

A real signup attempt failed with *"Could not create your account."* Asking
Supabase directly gave the true error:

```
{"code":500,"error_code":"unexpected_failure","msg":"Error sending confirmation email"}
```

**Cause:** Supabase's SMTP sender was `hello@highelmstudio.com`, authenticating
with an API key belonging to a **different Resend account**, and **no domain was
verified in Resend at all**. Resend refused the send.

The daily health digest kept working throughout, which is why this was invisible
— it sends from `onboarding@resend.dev`, Resend's shared sandbox address, which
proves the API key is valid and proves *nothing* about any domain.

### What fixed it

1. Resend verified `hotelcontentradar.com` (all three DNS records were already
   correct; see §6 for the check).
2. A new API key created on the **new** Resend account
   (`neil@hotelcontentradar.com`), scoped to sending for that domain.
3. Supabase SMTP updated: sender `hello@highelmstudio.com` →
   **`hello@hotelcontentradar.com`**, password → the new key. Sender name
   "Content Radar", host `smtp.resend.com`, port 587, username `resend` — all
   unchanged.

⚠ **The Supabase URL in the original version of this doc 404s.** Supabase has
moved the page. Don't hunt for a URL — use the click path: left sidebar
**Authentication** → **Emails** (or **SMTP** / **Settings** in that sub-menu).
The SMTP block is *below* the email templates and has its own Save button,
separate from the templates' one.

### Verified, not assumed

- **Signup probe returned clean** — a user object with `confirmation_sent_at`
  populated, no 500.
- **The email actually arrived**, from `hello@hotelcontentradar.com`. This
  second check is the one that matters: `confirmation_sent_at` only proves
  Supabase handed the message to Resend without SMTP rejecting it. It went to
  **spam** — see below.
- **Real-card end-to-end completed.** `subscriptions` row written at 11:35,
  `status: trialing`, `trial_end` 20 Aug, with `stripe_customer_id`
  `cus_V1SUyTINCEOsC8` and `stripe_subscription_id`
  `sub_1U1PZeALGYW26MHmGYyC0tkx` — and nothing but the webhook writes those, so
  the live webhook is proven working end to end.
- `user_id` on that row is `null`, and that is **by design, not a defect**. The
  gate in `lib/subscriptions.ts` is keyed entirely on email; `user_id` is never
  read. Don't "fix" it.
- The test ran on `nhpeacock@gmail.com`, which is on the admin allowlist — but
  that does **not** invalidate the gate test. `requireAdminUser` calls
  `requireActiveUser` first, so admins get no bypass; the subscription row is

### Left over from this section

  it charges a real card. It was run on Neil's own primary address rather than a

### Deliverability: the first email landed in spam

Not a misconfiguration. Every authentication record is present and correct —
SPF, DKIM, DMARC (`p=none`, reporting to `neil@`), plus the Google Workspace
apex SPF. It is simply that `hotelcontentradar.com` had never sent an email
before today, and Gmail is cautious with an unknown sending domain.

**Do not start changing DNS records over this.** They are right, and churning
them only discards the reputation being built. It improves with real sending
volume and engagement. Worth watching once there are real customers; if it
persists past the first dozen sends, revisit then.

## 7. Two things that look fine and are not proven

Both found on 6 Aug while answering ordinary questions, not while looking for
bugs. Neither is confirmed broken — that is the point. Each has a test below,
and the test is cheap. Run them before taking real customers.

### a. The Stripe Customer Portal has never been proven in LIVE mode

`/settings` has a **Manage billing** button opening Stripe's hosted Customer
Portal, where a member manages their card, sees invoices and **cancels**
(`app/api/billing-portal/route.ts`). The route is well built — it deliberately
requires only a session and *not* an active subscription, so a `past_due` or
cancelled member can still get in to fix their card.

But the Customer Portal has to be enabled in the Stripe Dashboard or
`sessions.create` throws — and **Stripe configures it separately for test and
live mode.** The route's own comment cites the *test* mode path. Nothing has
confirmed the live one exists.

If it isn't enabled, members cannot cancel from the product at all. That is not
a convenience issue; in the UK it is close to a consumer-rights one.

**Test:** sign in and click **Manage billing** at
https://www.hotelcontentradar.com/settings
- Portal opens → enabled, and a member can self-serve. Done.
- Inline error → live portal config is missing. The error text names the fix;
  it is normally Stripe Dashboard → Settings → Billing → Customer portal, with
  the mode toggle set to **live**.

### b. There is no session-refresh middleware, and a comment claims there is

`lib/supabase-server.ts` swallows a failed cookie write with:

> a failed write here is safe to ignore — middleware refreshes the session instead

**No `middleware.ts` exists.** Not in the repo at all. There is also no browser
Supabase client, and every other client sets `persistSession: false`. The
comment describes a component that was never written — a green-looking signal
over a thing that never happened, same as everything in §9.

What it means in plain terms: a member's access token expires after an hour. On
the next visit the app trades their long-lived refresh token for a fresh access
token, then tries to save it — and a Next.js Server Component render is not
allowed to write cookies, so the fresh token is computed and dropped. Route
Handlers *can* write cookies, so anything hitting an API route re-establishes
the session and masks this. A member who only reads pages has no working refresh
path.

Sessions themselves are fine and no "keep me signed in" option is needed —
Supabase issues persistent cookies, so members stay logged in across browser
restarts by default. This is specifically about *refresh*.

**Test:** log in, leave it well over an hour without touching the site, come
back and navigate between gated pages. Bounced to `/login` = real.

**Fix if real:** write the standard Supabase SSR `middleware.ts` — roughly 30
lines, runs before every request, refreshes the session and writes the cookie.
It is a documented pattern, not a design decision. Its own PR, with a test.

## 9. What these two days actually taught

Every failure had the same shape: **a green signal over a thing that had not
happened.**

- CI passed on a merge that never deployed.
- The health digest emailed successfully every morning while no domain was
  verified, because it sends from a sandbox address.
- Vercel held a live Stripe key from an entirely different account, and nothing
  compared it to anything.
- A webhook secret was simply absent, and would have surfaced only as a
  customer paying and receiving nothing.
- And once signup was fixed, the API returned a clean `confirmation_sent_at`
  over an email that had gone to spam. Every layer will happily report success
  for the part it owns. Only the inbox knows.

The repo's own `CLAUDE.md` already warns about this class: *"Green is not proof.
A check that has never failed may be incapable of failing."* Every fix in §2 and
§3 came from probing the live system directly, not from reading a dashboard.
Keep doing that.
