## 2. THE BLOCKER — nobody can sign up

A real signup attempt failed with *"Could not create your account."* Asking
Supabase directly gave the true error:

```
{"code":500,"error_code":"unexpected_failure","msg":"Error sending confirmation email"}
```

**Cause:** Supabase's SMTP sender is `hello@highelmstudio.com`, and **no domain
was verified in Resend at all**. Resend refused the send.

The daily health digest kept working throughout, which is why this was invisible
— it sends from `onboarding@resend.dev`, Resend's shared sandbox address, which
proves the API key is valid and proves *nothing* about any domain.

### Remaining steps, in order

1. **Wait for Resend to verify `hotelcontentradar.com`.** All three DNS records
   are confirmed live (see §6 for the check command). Click **Verify** again if
   it sits on Pending.
2. **Create an API key on the NEW Resend account** — https://resend.com/api-keys
3. **Update Supabase SMTP** — https://supabase.com/dashboard/project/dndefddhocxqczinfpfg/auth/emails
   - Sender email: `hello@highelmstudio.com` → **`hello@hotelcontentradar.com`**
   - SMTP password: the **new** account's API key. The one stored there belongs
     to the *old* Resend account and cannot send for this domain.
   - Leave sender name as "Content Radar", host `smtp.resend.com`, port 587.
4. **Add `hello@` as an alias** in Google Workspace (Admin → Users → Add
   alternate email). Not needed to *send* — needed so customer replies don't
   bounce.
5. **Re-run the signup probe** (§6). A clean result means signup works.
6. **Real-card end-to-end test**: incognito → `/start-trial` → fresh address
   (`nhpeacock+test1@gmail.com` style) → confirm email → log in → real card →
   expect the `/welcome` interstitial → dashboard. Then check a `subscriptions`
   row exists, check the delivery on Stripe's endpoint page, and cancel the
   subscription so it doesn't bill in 14 days.

## 8. What these two days actually taught

Every failure had the same shape: **a green signal over a thing that had not
happened.**

- CI passed on a merge that never deployed.
- The health digest emailed successfully every morning while no domain was
  verified, because it sends from a sandbox address.
- Vercel held a live Stripe key from an entirely different account, and nothing
  compared it to anything.
- A webhook secret was simply absent, and would have surfaced only as a
  customer paying and receiving nothing.

The repo's own `CLAUDE.md` already warns about this class: *"Green is not proof.
A check that has never failed may be incapable of failing."* Every fix in §2 and
§3 came from probing the live system directly, not from reading a dashboard.
Keep doing that.
